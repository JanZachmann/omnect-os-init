# Flash Mode 3 (URL download) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Port legacy `init.d/87-flash_mode_3` to Rust: download a `wic.xz` and its sha256 file from URLs held in the bootloader environment, verify the image, and flash it onto the running disk.

**Architecture:** Mode 3 adds `url.rs` to `src/mode/flash/` and reuses everything mode 2 built — `unmount.rs`, `net.rs`, `bmap.rs`, `rawio.rs`, `efi.rs`. The only mode-specific work is reading and base64-decoding the two URL keys, clearing them immediately, downloading with `curl`, and checking the sha256.

**Tech Stack:** Rust 2024, external `curl`, `dhcpcd`, `bmaptool`. Base64 decoding and sha256 verification are in-process.

**Spec:** `docs/superpowers/specs/2026-08-13-flash-modes-design.md` — §2.1, §3.1, §3.6, §5.3, §6, §8.

**Depends on:** `2026-09-21-flash-mode-1.md` and `2026-09-21-flash-mode-2.md`, both merged first. Mode 3 needs `net.rs`, `bmap.rs` and `unmount.rs` from the mode 2 plan, and the whole shared layer from the mode 1 plan.

---

## Baseline

Already present from the two earlier plans: the `flash-mode` shared layer, `FlashError` (including `NetworkFailed`), `BootEnvKey::FlashMode`, `unmount::unmount_target_disk` (mode 2 plan), `net::bring_up`, `bmap::copy`, `rawio::{copy_range, sync_all}`, `efi::handle`, the reboot terminal action for the network modes, and the best-effort log persistence after a successful flash.

Created here: `url.rs`, the `flash-mode-3` feature, `BootEnvKey::{FlashModeUrl, FlashModeUrlSha256}`, and a base64 decoder and sha256 check.

Mode 3 needs **no** new build-time constant.

## Global Constraints

Identical to the mode 1 plan. **Primary test feature combo for this work:** `--features uboot,gpt,flash-mode-3,test-utils`.

One addition specific to this plan: the two new dependencies for base64 and sha256 must be `default-features = false` and kept minimal — this binary ships in an initramfs. Use `base64 = { version = "0.22", default-features = false, features = ["std"] }` and `sha2 = { version = "0.10", default-features = false }`, both placed alphabetically in `Cargo.toml` and pulled in only by `flash-mode-3`.

- [ ] **Step 3: Implement**

```rust
const CURL_CMD: &str = "/usr/bin/curl";
const CURL_QUIET_FLAG: &str = "--no-progress-meter";
const CURL_FOLLOW_OUTPUT_FLAG: &str = "-Lo";
/// Skip certificate validation. Only used where the machine has no RTC:
/// without a trustworthy clock, certificate validity cannot be checked.
const CURL_INSECURE_FLAG: &str = "-k";
const RTC_MACHINE_FEATURE: &str = "rtc";
const DOWNLOAD_DIR: &str = "/tmp";
const IMAGE_FILE_NAME: &str = "wic.xz";
const SHA256_FILE_NAME: &str = "wic.xz.sha256";
const SHA256_HEX_LEN: usize = 64;
```

`curl_args` builds the vector and appends `CURL_INSECURE_FLAG` when `machine_features` has no exact `rtc` token — split on whitespace, never `contains`, so `efirtc` does not count.

`expected_sha256` takes the first whitespace-separated field of the first non-empty line and accepts it only when it is exactly `SHA256_HEX_LEN` ASCII hex characters.

`run_url`:

1. The caller in `mod.rs` has already cleared `flash-mode`. Read `flash-mode-url`, clear it, read `flash-mode-url-sha256`, clear it — each cleared immediately after it is read (spec §2.2). Then `decode_url` both.
2. `unmount_target_disk`, `net::bring_up`.
3. Download the sha256 file, then the image, each with `curl_args`.
4. Hash the downloaded image with `sha2::Sha256`, streaming it in `COPY_BUFFER_SIZE` chunks so a multi-gigabyte image is never held in RAM, and compare against `expected_sha256`. A mismatch is `FlashError::CopyFailed` naming both digests.
5. `bmap::copy` with `bmap: None` — the `--nobmap` form — from the image onto `/dev/omnect/rootblk`.
6. `efi::handle`, `sync_all`, log, reboot.

Add the `FlashMode::Mode3` dispatch arm in `mod.rs`, reusing the network modes' reboot terminal action and the after-success log persistence.

## Companion work (not this repo)

Spec §12 lists the meta-omnect changes that follow all three modes. Track them there, per the cross-repo workflow — do not implement them here:

- pass `OMNECT_PART_OFFSET_BOOT`, `OMNECT_PART_SIZE_BOOT` and `OMNECT_FLASH_MODE_2_DIRECT_FLASHING` into the `omnect-os-init` build environment;
- map `DISTRO_FEATURES` `flash-mode-2` and `flash-mode-3` onto the Cargo features, and gate mode 1 the same way, dropping it from `default`;
- retire `init.d/87-flash_mode_{1,2,3}` and the `sed` substitutions in `omnect-os-initramfs-scripts.bb`;
- drop `util-linux-uuidgen` from the initramfs: `uuidgen` was called from `flash-mode-1` and nowhere else, and the Rust port generates the UUID itself;
- no other package changes are needed — every tool the three modes use is already installed.
